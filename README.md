# Lamprey Dashboard

Live dashboard of PIT-tag data for translocated Pacific Lamprey
(adult and juvenile) in the Methow subbasin, plus Wells Dam
adult-passage counts. PTAGIS data is refreshed weekly by a
GitHub Action; the Shiny app reads the committed CSVs.

```
lamprey-dashboard/
├── .github/workflows/weekly-pull.yml  # cron -> R/fetch_*.R + R/build_*.R
├── R/
│   ├── fetch_ptagis.R                 # weekly PTAGIS exports
│   ├── build_site_metadata.R          # PTAGIS sites (lat/lon)
│   ├── fetch_dart_wells.R             # Wells Dam Pacific Lamprey counts
│   └── build_lamprey_data.R           # joins raw pulls -> app-facing CSVs
├── config/
│   ├── queries.yml                            # PTAGIS user + filenames
│   ├── site_metadata.csv                       # auto-generated
│   ├── site_coords_supplemental.csv             # hand-curated site gaps
│   ├── lamprey_release_site_overrides.csv       # corrected release coords
│   └── legacy_release_site_notes.csv            # older/partial notes, reference only
├── data/                              # auto-updated CSVs
│   └── raw/                           # timestamped archive of each pull
├── app/
│   ├── app.R                          # Shiny dashboard
│   └── deploy.R                       # shinyapps.io deploy helper
└── DESCRIPTION
```

## How the data pipeline works

PTAGIS's Advanced Reporting (SAP BusinessObjects) doesn't give
saved queries a direct CSV download URL. The supported pattern
is:

1. **On PTAGIS:** save your query, then *Subscribe To -> File*
   to schedule it to write a CSV to your user's file store on a
   recurring basis.
2. **PTAGIS serves the file** at:
   `https://api.ptagis.org/reporting/reports/<user>/file/<filename>.csv`
3. **The GitHub Action** hits that URL weekly, saves the raw CSV
   in the repo, joins/transforms it into the CSVs the app reads,
   and commits.

Site coordinates come from `https://api.ptagis.org/sites/...`
and are cached weekly to `config/site_metadata.csv`. That API
doesn't cover a couple of MRR trap sites the juvenile data needs
(`METTRP`, `TWITRP`) -- `config/site_coords_supplemental.csv` is
a small hand-curated file that fills that gap; the app and the
build script both merge it in, with the supplemental file
winning on conflicts.

Wells Dam adult Pacific Lamprey counts come from CBR DART's
Adult Daily Counts CSV endpoint (`R/fetch_dart_wells.R`), one GET
per year, 2010 through the current year, extracting the
`LmpryDay` / `LmpryDay10Yr` columns. Years with no data yet
return an HTML error page from DART; the script detects that and
skips silently.

The Wells Dam tab's daily count table shows a running
**Cumulative Count** and **Cumulative 10-yr avg** alongside the
raw daily values. Both are computed over the full season
(including zero-count days) before the table is filtered down to
days with fish, so a day with no passage this year but nonzero
historical activity still contributes correctly to the
cumulative average.

### Release-site coordinate correction

PTAGIS's own "release site" field on the Complete Tag History
export is the generic site record (e.g. the Methow River mouth)
rather than the actual translocation drop point. Historically,
someone manually corrected 4765 tags' release site/lat/lon by
cross-referencing field notes -- that correction is preserved in
`config/lamprey_release_site_overrides.csv` and joined in by
`tag_code` every week. **This file is static**; it's not
regenerated by the pipeline. Any new tag added to PTAGIS after
this file was built falls back to PTAGIS's own (less precise)
release-site coordinate, resolved by looking up the release
site's code against `config/site_metadata.csv` +
`config/site_coords_supplemental.csv`. If you get more precise
field data for new releases, add a row to
`config/lamprey_release_site_overrides.csv` by hand (columns:
`tag_code, event_type_name, event_site_name, event_date_mmddyyyy,
event_release_site_name, event_release_date_mmddyyyy,
mark_date_mmddyyyy, event_comment_value,
event_release_site_latitude_value,
event_release_site_longitude_value, cth_count`) and it'll be
picked up on the next weekly run.
`config/legacy_release_site_notes.csv` is an older, partial
version of this same idea, kept only for provenance -- the
pipeline doesn't read it.

## One-time setup

### 1. Verify saved queries in PTAGIS

Log into <https://www.ptagis.org/> and open **Advanced Reporting**.
This pipeline needs 4 saved queries (already in
`config/queries.yml`, and already present under this account as
of this writing, but currently only as one-off exports):

- `Translocated Lamprey Complete Tag History` -- Complete Tag
  History, translocated Pacific Lamprey (adult releases)
- `Translocated Lamprey Interrogation Summary` -- Interrogation
  Summary, translocated Pacific Lamprey (adult detections)
- `Juv Lamprey Tagging Detail` -- Tagging Detail, juvenile
  Pacific Lamprey
- `Juv Lamprey Interrogation Summary` -- Interrogation Summary,
  juvenile Pacific Lamprey

**For each query, set (or confirm) a recurring export:**
**Subscribe To -> File**, format **CSV**, frequency **Weekly**
(e.g. Sunday night, so Monday's Action run picks up fresh data).
Without this, the Action will keep re-fetching the same stale
snapshot.

### 2. Edit `config/queries.yml`

Set `ptagis_user` to the PTAGIS account that owns the
subscriptions (currently `cdkyger`). Each `filename` must match
exactly what PTAGIS writes (capitalisation and spaces matter).

### 3. (Optional) PTAGIS credentials

Scheduled-export files are served openly via the API, so no auth
is needed. If that ever changes, add `PTAGIS_USER` and
`PTAGIS_PASS` as repo secrets and the script will use them.

### 4. Push to GitHub and trigger the first run

In **Actions -> Weekly PTAGIS pull -> Run workflow**. After it
succeeds, CSVs appear in `data/` committed by
`github-actions[bot]`. From then on it runs automatically every
Monday at 8am Pacific.

## Running the app locally

From R at the project root:

```r
# install deps once
install.packages(c("shiny", "bslib", "dplyr", "readr",
                   "stringr", "lubridate", "leaflet", "plotly", "DT"))

shiny::runApp("app")
```

The app loads CSVs from `data/`/`config/` if they exist locally,
otherwise falls back to the raw GitHub URLs.

## Deploying to shinyapps.io

### One-time

1. Create/use a shinyapps.io account (`douglaspud-nr`).
2. **Account -> Tokens -> Show -> Show secret -> Copy to clipboard**.
   This puts a `rsconnect::setAccountInfo(...)` line on your
   clipboard.
3. In R, paste and run that line. You're now authenticated.

### Each deploy

```r
source("app/deploy.R")
```

This deploys just `app/app.R`. The app fetches data at runtime
from the raw GitHub URLs, so you don't need to redeploy when the
data updates -- the weekly Action is enough. Re-deploy only when
the app code changes.

## Output files

- `data/<query_name>.csv` -- latest raw snapshot of each PTAGIS
  query, overwritten each pull.
- `data/raw/<query_name>_<timestamp>.csv` -- archive of each
  pull. Prune periodically if the repo grows.
- `data/last_update.csv` -- one row per query with row count and
  fetch timestamp.
- `data/releases.csv`, `data/detections.csv`,
  `data/juv_releases.csv`, `data/juv_detections.csv`,
  `data/wells_lamprey_counts.csv` -- the app-facing CSVs built by
  `R/build_lamprey_data.R` / `R/fetch_dart_wells.R`.
- `config/site_metadata.csv` -- cached PTAGIS site list with
  lat/lon.

## Notes / caveats

- **Two of the four PTAGIS exports (`Juv Lamprey Tagging
  Detail.csv`, `Juv Lamprey Interrogation Summary.csv`) are
  UTF-16 LE with a BOM** (the SAP BusinessObjects default). The
  fetch script detects the BOM and re-encodes everything to UTF-8
  before saving.
- PTAGIS has a reporting lag; "last detection" means "last
  detection PTAGIS has received and processed."
- shinyapps.io free tier sleeps inactive apps -- first hit after
  idle takes a few seconds.
